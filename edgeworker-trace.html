Sitecore Personalize EdgeWorker · architecture & verification

One URL, five cached homepages, zero origin hits.

Today every personalized homepage request runs the decision inside the Next.js middleware at the origin, so the page can never be cached. This EdgeWorker moves the Sitecore Personalize decision to the Akamai edge, before cache lookup. Akamai asks Personalize which variant the visitor belongs to, then serves that variant's already-cached HTML. The visitor's address bar still says /; only Akamai's cache key and the forward request know about the variant.

The homepage has four variants, and every one of them is a signed-in state — booked, courtesy hold, non-booked, recently searched. That single fact shapes most of what follows.

01

The short version

Six things happen. Everything else on this page is a zoom-in on one of them.

A

The request reaches Akamai

A visitor asks for the homepage. It lands on the nearest Akamai edge server, not on our servers.

B

Akamai gathers the visitor's context

It reads the visitor's cookies — including cclUser, which only exists once someone has signed in — and their Personalize browser id.

C

Personalize picks a variant

Akamai calls the Personalize flow with that context. The flow answers with one of four signed-in variants — or nothing, which means “show the standard page”.

D

Akamai checks its cache for that variant

Each variant has its own cached copy of the homepage. If Akamai already holds one, it is returned immediately and our origin is never touched.

E

Only on a miss: the origin renders

Akamai fetches that one variant from the Next.js app running in Kubernetes, then stores it for everyone else in the same bucket.

F

The visitor gets the page, analytics get the decision

Cookies carry the browser id and the decision back to the browser, which forwards it to GTM and Tealium. The URL never changed.

Every variant requires a sign-in — which changes the maths

All four names begin Logged-In-. A signed-out visitor cannot match any of them, so they land on default. Since most homepage traffic is signed out, default is not an edge case or a control group — it is the busiest bucket on the site, and its cache hit rate is what decides whether this project pays for itself.

4 items under /Page Variants

The browser-id call only ever fires for a visitor who gets default

The bid_ cookie is written on a visitor's very first request. cclUser is written later, at sign-in. So anyone who could match a variant already has a browser id — meaning browser/create only ever runs for a first-touch, signed-out visitor whose answer is guaranteed to be default. Up to a second of added latency, plus a new CDP guest record, spent on a question with a known answer.

Why caching a signed-in page is safe here

The variant HTML is generic. Names, booking numbers and hold expiry are read from cookies in the browser after hydration — HeroBanner and CourtesyHoldHero both do their parseCookie work inside useEffect, so nothing personal reaches the server render. Every component on all four variants has to keep that property, or one guest's data gets cached and served to the whole bucket.

04

Why the cache doesn't collide

The whole design rests on one line: the worker adds a Property Manager variable to Akamai's cache key. Same URL, different bucket, different cached object — five of them.

https://www.carnival.com / (query params, minus utm_*) + PMUSER_EW_BUCKET

request.cacheKey.includeVariable('PMUSER_EW_BUCKET') runs on every request to a configured route — hits and misses alike — so the key space stays consistent. The variable must be declared in Property Manager first; setVariable() throws if it isn't.
